Como o app foi construído

O mesmo código de interface roda no aplicativo e na versão web. A diferença fica só na camada de armazenamento — o domínio não sabe onde os dados moram.

Interface React 19 · TypeScript · Vite · Tailwind telas, componentes e estado da sessão
↓
Regras e dados Serviços · repositórios · StorageAdapter contrato único de chave-valor, independente do alvo
↓
App desktop SQLite via Rust %APPDATA%\br.com.clinicapsi.prontuario
Versão web localStorage usada nos testes automatizados

Por que um app de desktop?

  • Sem teto de 5 MB: o navegador limita o localStorage; o SQLite não.
  • Dados no computador da clínica: nada é enviado para servidores de terceiros.
  • Backup consistente: o Rust copia o banco com o aplicativo aberto.
  • Sem administrador: o instalador coloca o app só para o usuário.

A falha intermitente que apareceu na validação

Durante os testes, uma verificação passou a falhar de vez em quando: o painel dizia que o profissional tinha 0 pacientes, mesmo com o paciente aparecendo na mesma tela. Investigamos até a causa — e ela não estava no sistema.

01

O sintoma

Em 4 de cada 10 execuções o teste falhava com “esperava 1, recebeu 0”. Na repetição seguinte, passava — o clássico problema que some quando alguém vai olhar.

02

A causa

O painel abre mostrando zero e só depois de buscar os dados troca pelo número real. O teste lia o valor nesse intervalo. A prova veio da própria captura automática feita no instante da falha: nela o painel já mostrava 1.

03

A correção

O teste passou a esperar o painel montar antes de ler o número. Nenhum atalho: não escondemos a mensagem de erro nem afrouxamos a verificação — a leitura é que estava cedo demais.

10/10execuções do teste corrigido, sem falha
27/27execuções do arquivo de testes completo
0erros de tipagem após a mudança

O aplicativo não precisou ser alterado para o teste passar — o comportamento dele estava correto. Só o teste estava impaciente. Ler o relatório de continuidade (registro da investigação, escrito antes da correção)
